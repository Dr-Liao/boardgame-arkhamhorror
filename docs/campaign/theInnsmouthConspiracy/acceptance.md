# 《印斯茅斯暗潮》验收条件（AI 验收清单）

本文件把六循环（TIC，The Innsmouth Conspiracy）的验收条件固化为可执行清单，供后续 AI 或维护者每轮独立复核使用。它是[内容迁移规范](../../arkham-content-migration.md)、[卡牌模型](../../card-model.md)、[架构约定](../../../ARCHITECTURE.md)与[冒险指南要求](../../scenario-guides.md)在 TIC 上的**验收执行口径**，不替代那些规范本身。

- 范围：六循环全部卡片（`ticCampaign` 252 + `ticInvestigators` 16 + `ticPlayer` 93 = 361 条记录）、8 章场景、4 个幕间、14 个记忆闪回、战役流程与 TIC 交互。
- 结论格式：每轮验收必须在 `artifacts/migration/<cycle>/`（或大厅根 `artifacts/`，不签入）输出逐卡/逐章判定与命令日志，并把稳定的证据写回 `audit/` 或对应测试。
- 本文件只列**验收条件与判定方法**；当前实现状态以代码、测试和可复算证据为准，不以账本/文档自述为准。

## 0. 验收原则（不可协商）

1. **独立复核**：不采信 `audit/tic-*.json` 的 `verified`、README 的完成勾选或测试标题，只采信「卡面 + 实现文件 + 引擎读点 + 可复现证据」。
2. **卡面优先**：中英文卡面（`cards-data.js`/官方卡表）是最终标准；参考实现（`参考资源/ArkhamHorror-main/`）只作第二来源，冲突时以卡面为准并记录差异。
3. **测试通过 ≠ 玩家可达**：必须区分「测试直接调用 `executeDescriptor`/手工开窗」与「经 `legalMoves → validateMove → applyMove` 或真实事件窗口枚举」。验收只认后者（脚本/夹具可辅助，但必须走到真实入口）。
4. **声明即接线**：条目新增的任何字段、规则键、flag 都必须在同一轮有引擎或内容层读点；`grep` 找不到读点即按未实现计，不得写进账本。
5. **原语优先**：卡只能使用已登记原语；发现同一句规则被第二张卡复制时按原语候选处理，第三张前停止写卡。绕过已有原语另写降级实现（尤其是带「未来原语」注释的死分支）按缺陷计。
6. **零隐瞒**：`simplified`/近似/阻塞必须显式登记，不能混进 `verified`；账本 `--check` 不通过时不得宣称完成。
7. **工作区稳定**：验收期间源码哈希必须稳定；源码变化后旧证据一律失效，需重新生成。

判定词：`MATCH`（逐句/逐数值一致且有真实读点）、`PARTIAL`（主体一致但有条件/数值/可达性偏差）、`WRONG`（核心效果与卡面相反或失效）、`MISSING`（无行为/未接线）、`NO_SPECIAL_TEXT`（卡面无特殊规则文本）、`UNVERIFIABLE`（缺来源或不可判定，必须写明缺什么）。**只有 MATCH 计入验收完成；PARTIAL/WRONG/MISSING 必须逐项修复或登记未完成。**

## 1. 卡牌验收（逐卡）

### 1.1 所有卡（玩家卡与非玩家卡共同）

- [ ] 卡号、名称、类型、正反面与 `cards-data` 一致；条目 `code` = 文件名，索引已重建（`cards:check` / `cards:encounter-check`）。
- [ ] 费用/打出条件：行动、资源、线索、使用次数、封印/标记、经验与快速时机；打出通道（手牌/弃牌堆/威胁区/宿主下方/原区）与卡面一致。
- [ ] 目标与范围：目标类型、可选性、范围与合法性条件（同地点/连接/任意）与卡面一致。
- [ ] 时机窗口：触发种类与窗口 id 已在 `src/engine/windows.js` 注册，且有真实调用点；不是「注册了但永不打开」。
- [ ] 数值：技能/难度、伤害/恐惧、线索/资源/毁灭、牌数、生命/理智等逐数字对照。
- [ ] 次数限制：每检定/每阶段/每轮/每回合/每场/每战役、`owner`（实例/调查员/玩家/团队）与卡面一致；`perTest`/`perWindow` 的键必须能区分不同事件。
- [ ] 区域与去向：弃置/移出游戏/胜利区/威胁区/旁置/牌库顶底/宿主下方，结算后唯一且守恒。
- [ ] 成功/失败/取消/重试分支齐全；负面路径（无目标、不足费用、目标非法）拒绝且不留下部分状态。
- [ ] 可达性：`action`/`free` 能力在条件满足时出现在 `legalMoves`；`reaction`/`forced` 描述子在真实事件路径被枚举（不是测试手工开窗）；不出现「越界可达」（别人/别地点被错误提供）。
- [ ] 测试：标题含卡号，断言卡面行为（数值、分支、限制、负面路径），而不是只断言标志位/文件存在。
- [ ] 存档/重放：涉及可变状态（下方牌、捕获、封印、限制记账、待决选择）的卡，JSON 往返与重放一致。

### 1.2 玩家卡与调查员（额外）

- [ ] 打出费用/槽位/多职阶/经验/卓越/永久/重印别名（`duplicateOfCode` 只保留 canonical 实现）正确。
- [ ] 构筑：职业/等级/特性限制、专属卡与专属弱点只进对应牌组、不进入一般卡池。
- [ ] 调查员：卡面能力、旧印、轮末/检定窗口、下方牌（beneath）放置与投入/收回、专属依赖、构筑合法性。
- [ ] 标记交互：祝福/诅咒的封印、替换、追加揭示、取消、检后归还，全部经 `chaosTokens` 原语。
- [ ] 隐私：手中牌、下方牌、私有候选、封印标记不得进入其他观察者投影。
- [ ] 弱点：揭示结算、去向、不可主动打出/仅特定通道可打出等条件符合卡面。

### 1.3 非玩家卡（额外）

- [ ] 敌人：生成（含印刷生成点/任意空地点/线索最多等）、猎手/猎物/冷漠/巨大/反击/威吓、生命/战斗/躲避、击败/躲避去向与胜利点。
- [ ] 诡计：显现检定/替代结算（`encounterResolve`）、进入威胁区/弃牌堆/旁置/附属的去向、涌动/险境/不可取消。
- [ ] 地点：shroud/线索（固定/每人）/胜利点/特性/淹没初始值/连接（含正反面与揭示后的连接守恒）/隐藏身份/入场规则。
- [ ] 幕/议程：`objective`/`onReveal`/`onRoundEnd`/阈值/背面结算、可选推进与全员撤退钩子（`allResigned`）、记录写入。
- [ ] 剧情资产：归属、控制者、槽位豁免、移除游戏而不进弃牌堆、离场清理；载具需同时注销载具登记。
- [ ] 共享遭遇组与跨循环依赖：组内每张卡都要有可命中的条目（含数字卡号与历史别名映射）；缺条目时抽取不得静默空转。

### 1.4 逐卡记录

每张卡输出一行，至少包含：`code / 判定 / 实现文件:行 / 卡面依据 / 读点或可达路径 / 测试文件:标题 / 问题与严重度`。不得用「文件存在 + 任一测试通过」判定 MATCH。

## 2. 原语验收

- [ ] 文档登记的原语真实存在于 `src/engine/**` 或内容共享工厂，且条目实际调用的 `ctx.api.*` 路径都有定义（不得有 `typeof api.foo === 'function'` 的死探测长期存在）。
- [ ] 每个原语具备：引擎读点、正常路径、负面路径、JSON 存档往返、确定性重放；涉及选择的交互必须在事务/待决选择内完成。
- [ ] 新增或修改原语须同步更新 `docs/card-model.md`/`docs/theInnsmouthConspiracy/primitives.md` 与本清单的回归项。
- [ ] 高风险原语回归集（本轮审计已发现缺陷的类别，修复后必须长期回归）：
  - `limit.perWindow` / `limit.perTest` 的实例键必须区分「同一阶段的不同事件」与「同一窗口」；07006、07012、07158、07121 为历史反例。
  - 载具移动与事件时序：驶离事件必须在乘客仍视为在出发地时结算（或允许按乘客快照付款）；道路危害付款人=出发地调查员（含乘客）。
  - 祝福/诅咒物理池满时 `replace` 不得静默丢标记；替换选项必须按剩余池门控。
  - 「你可以选择推进」类幕目标必须保留玩家选择权，不得自动推进。
  - 动态地点符号连接：印刷图标面（front/back）与数据口径一致；揭示不得销毁已建立的印刷连接。
  - 事件窗口门禁必须用 `hasWindowListener` 类全量探测（含非玩家实体），不得只按某个调查员旧式反应开关。
  - 翻面/钥匙费用等物理实体原语（07300）必须有真实写入口。

## 3. 场景验收（8 章，每章逐项）

每章必须按路线图 §6 的 12 项逐项给出证据，全部满足才可标注该章验收通过。最低要求：

### 3.1 设置与区域守恒

- [ ] 起始地点、初始揭示、初始地点数/随机变体、随机池物理卡总数守恒（多物理副本按 `id#n` 区分）。
- [ ] 遭遇牌库：组来源、每卡副本数、初始抽取、保留/旁置卡的数量与来源、洗回规则。
- [ ] 钥匙：颜色、正面/背面、持有者（调查员/地点/敌人/旁置/移出）；隐藏钥匙不泄露。
- [ ] 混乱袋：四档难度、永久标记、追加标记、封印，与来源锁一致。
- [ ] 淹没/屏障/载具/道路等初始机制状态；载具乘客与驾驶者。

### 3.2 幕与议程（推进必须符合卡面）

- [ ] 顺序、阶段号、doom 阈值/线索目标与印刷一致（含按人数、按记录、变体选择）。
- [ ] 推进条件：自动推进 / 玩家可选推进 / 全员撤退（`allResigned`）/ 特殊记录条件，逐条与卡面一致。
- [ ] 正反面：背面全部效果（翻面奖励、地点/敌人布置、记录、混乱袋、直接推进到 Xa 等）逐句核对。
- [ ] 幕/议程上的 `scriptCard` 行动出现在剧本书对应卡片旁，不可用时给出原因。

### 3.3 地点与连接

- [ ] 每个地点的 shroud/线索/胜利点/特性与印刷/参考一致（数值脚本比对 + 抽样人工）。
- [ ] 连接：印刷连接、符号连接、道路/网格连接；揭示、移动、地点移除后仍守恒；隐藏身份地点未揭示时不泄露名称/数值。
- [ ] 地点入场/离场规则（淹没入场、隐藏地点、动态扩展）与卡面一致；移除地点时同步清理连接与承载区。

### 3.4 遭遇与结局

- [ ] 本章敌人/诡计/剧情资产逐张可触发；专属与共享遭遇组无缺失、无空转。
- [ ] 全部结局键（R1..R8、noResolution 等）可达：每条结局给出一条真实驱动路径（不是直接调 `finish/resolution`）。
- [ ] 结局结算：记录、经验（含 bonus/替代）、创伤、击败/撤退、奖励卡、混乱袋变化、`campaign.failed` 与后续节点正确。
- [ ] 跨章记录：本章写入的记录被后续章/幕间正确读取（记录矩阵逐项核对）。

### 3.5 剧情与指南

- [ ] 完整中英文指南：开场及条件分支、完整设置、特别规则、后续剧情、结局与结算；特别规则优先、结局默认折叠；固定入口位于剧本书右侧、混乱提示卡下方。
- [ ] 叙事只投影已到达且有权查看的分支；历史正文不被改写；中英内容一致（缺译要显式标记）。
- [ ] 卡背要求的幕间/闪回正文必须存在于 `story-text`/指南；缺正文按验收缺口计。

### 3.6 存档、重放与多人

- [ ] 章节中 JSON 往返后 `legalMoves` 与状态一致，继续推进结果一致。
- [ ] 待决选择/私有信息恢复一致；重放确定性（固定种子逐步哈希一致）。
- [ ] 多人：逐席位投影隐私正确；非房主/非当前回合/错座位动作被拒且不改状态。

### 3.7 每章必须真实大厅验收

桌面 1440 与移动 390 各至少一条真实大厅 HTTP 链路（选人→构筑→开局→章内推进→结局/交接）；章节夹具与直调 API 只能补充，不能替代真实路线。

## 4. 战役流程与剧情验收

- [ ] `content/campaigns/theInnsmouthConspiracy/flow.js` 节点顺序/unlock/升级窗口与参考 `Campaign/Campaigns/TheInnsmouthConspiracy.hs` 的 `nextStep` 对应（含 `continueNoUpgrade` 节点）。
- [ ] 幕间 I–IV：剧本键、XP/永久混乱标记、钥匙奖励、灯塔记录、同伴发卡与移除选择逐条核对。
- [ ] 闪回 1–14：触发地点/条件、记忆写入、钥匙/遗物/混乱标记/记录变化、重复结算保护；闪回 XIV 的并行幕 07317/07318 分支。
- [ ] 尾声：记忆集合判定、`TheHorribleTruth` 记录、闪回 XV 分支、战后记录正确。

- [ ] 战役结局判定：每个可达结局都有对应 `endings` 标签与结算。

## 5. 交互与玩家可达验收

- [ ] 封印/释放、钥匙（隐藏/转交/花费）、载具（进入/离开/驾驶/容量）、淹没/空气、原区投入/收回、捕获/押送、并行幕、道路/车辆等 TIC 交互经真实大厅 HTTP 与浏览器验证；桌面/移动各覆盖合法、非法、空状态、取消/重试与键盘焦点。
- [ ] 每张有 `action`/`free` 能力的卡：条件满足时在 `legalMoves` 可见（至少一次，测试内断言）；反应/强制描述子至少一次经真实事件窗口枚举。
- [ ] 不得出现「只能通过测试直调触发」的能力；不得出现「越界可达」（对非控制者/异地开放）。
- [ ] 特殊卡面行动归属（`scriptCard`）、不可用原因、已用次数展示正确。

## 8. 完成判定（Gate）

一轮验收只有同时满足以下条件才算完成：

1. 8 章全部「可跑通」，每章所有结局（含失败/撤退/特殊分支）至少各有一条真实可达路径；不存在「场景不可通关」「条件永不满足」「清理后死锁」。
2. 361 条范围卡：`MISSING = 0`、`WRONG = 0`、未解释的 `PARTIAL = 0`；任何简化/近似都在账本中显式登记并在 README 披露，不计入 verified。
3. 第 6 节 HIGH 回归清单全部有自动化用例并通过；非 HIGH 回归项有对应修复记录。
4. 所有声明的原语都有读点、测试与存档/重放覆盖；不存在「声明没人读」「只有测试直调可达」。
5. 真实浏览器：交互验收与发布验收（桌面 1440 / 移动 390）通过；无页面错误、无横向溢出。
6. `audit-tic.mjs --check`、`audit-tic-scenarios.mjs --check`、`audit-tic-all-cards.mjs --check` 全部 exit 0；文档/README 的完成声明与账本、代码一致。
7. 工作区干净：验收期间源码哈希稳定；仓库源码/测试/账本无未经审阅的改动。

若任一条不满足，README/路线图不得标记完成，账本不得把对应条目标为 `verified`。
