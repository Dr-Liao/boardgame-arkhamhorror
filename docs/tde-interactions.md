## 1. 证据口径

- 交互状态必须由服务端 `requestChoice` / `presentation-state` / 观察投影产生，浏览器只提交 `legalMoves` 中的动作；私有候选、手牌、牌库顺序不得进入其他座位投影。
- 每个交互必须有：可用路径、不可用原因、空状态、取消/重试；桌面 1440×900 与移动 390×844 各至少一条真实操作路径 + 截图。
- 新交互先于批量卡牌；复用 `web/` 现有组件、CSS 变量与交互模式，**不得**按卡号写 UI 分支。

### 2.1 开局交互的硬口径（§1.4.1）

- 人数校验前置到 hub：`playerCount` 为奇数时「并行双线」置灰并给原因；`playerCount = 1` 只保留两个单线选项。
- 分选双线要求两线各 ≥1 座位；某线 0 人时按单线处理并在开局确认里显式说明，不静默开局。
- 每个房间座位只走一次选人/构筑；跨线重复调查员校验保留；缺牌组阻塞并给原因，不静默待机。

### 2.2 场景交互的口径来源

- 蜂拥卡面板：P3 的 `swarm.placeCards` 决定入口数据；面板只展示与选择，不做规则判断。
- 掩藏地点：A2 的 15 张 b 面故事卡与 B3 的 8 张洗回牌堆是两种收尾，翻面面板要能表达。
- 隐藏手牌：18 张全部带 Peril；06306–06310 的敌人形态要在手牌里提供攻击/躲避入口。
- 纵向堆叠：布局必须复用既有 layout 变量，不新建循环专属布局。

## 4. 边界

- 交互不是规则：面板只把已算好的候选呈现出来；规则判断留在引擎与描述子。
- 双线（`parallel`）的 UI 仍是「一个房间、每座位只看本线」，但开闸门禁在 §11.2，不随 P5 一起放开。
- 当前只有 2 条登记在 P2；其余 8 条没有账本证据，P4 定稿前不得在卡牌批次里临时拼面板。
